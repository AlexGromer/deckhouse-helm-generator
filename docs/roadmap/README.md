# Дорожная карта dhg: эпики, спецификации, задачи

Каталог описывает **всю запланированную работу** так, чтобы её мог выполнить агент без устного контекста: что делать, зачем, как устроено и как проверить готовность.

**Статус каталога:** проработка. Реализация начинается только после явного разрешения владельца проекта (см. раздел «Порядок работы агента»).

## 1. Граница проекта

Суть dhg: **факты о приложении → Helm chart этого приложения**. Факты берутся из манифестов, кластера, GitOps-репозитория, образа, docker-compose или исходников.

Критерий, входит ли объект в scope: **живёт ли он в жизненном цикле релиза приложения**.

| В scope | Вне scope (платформа) |
|---|---|
| Объект namespaced, создаётся и удаляется вместе с приложением, настраивается командой приложения: `ServiceMonitor`, `HTTPRoute`, `CiliumNetworkPolicy`, `KafkaTopic`/`KafkaUser`, `PodLoggingConfig`, DNS-настройки пода | Cluster-scoped объекты платформенной команды: настройки CNI Cilium, CoreDNS, IngressClass, ClusterIssuer, `ModuleConfig` модулей Deckhouse (`cni-cilium`, `kube-dns`) |

Платформенным объектам место в платформенном GitOps-репозитории или в модуле Deckhouse. Для модуля в dhg уже есть `pkg/generator/modulescaffold.go`.

Принципы, обязательные для всех эпиков (ADR-049, ADR-053, ADR-059):

- **Только факты.** То, что не выводится из входа, не подставляется. Такие пункты перечисляются в отчёте (`SYNTHESIS.md` или stderr `Note:`) или выносятся в values с пустым либо явно помеченным значением.
- **Идентичность объектов сохраняется**: имена, метки, селекторы (ADR-049).
- **Каждый сгенерированный chart проходит Helm** (`helm lint --strict`, `helm template`) во всех режимах: `universal`, `separate`, `library`, `umbrella`.
- **Новые зависимости — только с обоснованием в ADR** (по умолчанию стандартная библиотека и уже подключённые модули).

## 2. Структура каталога

```
docs/roadmap/
├── README.md              ← этот файл: правила, контракты, порядок
├── BACKLOG.md             ← индекс всех эпиков и задач со статусами
├── _template/             ← шаблоны документов
│   ├── README.md
│   ├── spec.md
│   ├── design.md
│   └── tasks/NN-task.md
└── EPIC-NN-<имя>/
    ├── README.md          ← обзор: проблема, цель, scope, зависимости, порядок задач
    ├── spec.md            ← ЧТО: требования, контракты CLI/values/отчёта, критерии приёмки
    ├── design.md          ← КАК: архитектура, потоки данных, альтернативы, ADR-кандидаты
    └── tasks/
        └── NN-<имя>.md    ← атомарная задача (≈ один PR)
```

Документы пишутся на русском. Технические термины — на английском, с пояснением при первом упоминании. Пути — относительно корня репозитория.

## 3. Общие контракты

Контракты, которыми пользуются несколько эпиков. **Владелец** определяет контракт в своём `design.md`. Остальные эпики ссылаются на него и не переопределяют. Нужное расширение описывается в своём `design.md` в разделе «Запросы к другим эпикам».

| Контракт | Владелец | Пользователи |
|---|---|---|
| Новые типы связей в `pkg/types` (`RelationshipType`): вызов сервиса по адресу, вызов внешнего хоста, публикация и потребление топика брокера; логические узлы графа для внешних систем и топиков | EPIC-03 | EPIC-02, EPIC-04, EPIC-08, EPIC-09 |
| Извлечение адресов и параметров подключения из env и конфигов (URL, JDBC, bootstrap servers, issuer). Общий парсер для манифестов и для `pkg/synth` | EPIC-03 | EPIC-02, EPIC-04, EPIC-08, EPIC-09 |
| Модель группировки «сервис → PBC → продукт» (метка `app.kubernetes.io/part-of`) и вложенный umbrella | EPIC-03 | EPIC-04 (границы политик), EPIC-02 (ACL по границам) |
| Регистрация опциональных возможностей `--with` (ADR-046, `pkg/generator/features*.go`) | существующий код | все |
| Отчёт о невыводимом: `SYNTHESIS.md` и `Note:` (ADR-059, `pkg/synth/report.go`) | существующий код | все |

**Номера ADR.** В `design.md` решения оформляются как **ADR-кандидаты без номера** («ADR-кандидат: …»). Номер присваивается при реализации: следующий свободный в `docs/ADR.md`.

## 4. Порядок работы агента

1. **Получить разрешение.** Реализация задач этого каталога начинается только после явного разрешения владельца проекта на конкретный эпик или задачу.
2. **Выбрать задачу** в `BACKLOG.md`: статус `ready`, все зависимости (`Depends on`) в статусе `done`.
3. **Прочитать** README, `spec.md` и `design.md` эпика, затем файл задачи. Если факт в документе помечен «не проверено», проверить его до реализации. При расхождении остановиться и описать расхождение в задаче.
4. **Ветка:** `roadmap/EPIC-NN/NN-<имя>` от актуального `main`. Одна задача — один PR.
5. **Реализовать** по разделу «Изменения» задачи. Изменение за пределами описанных файлов — только при необходимости, с объяснением в PR.
6. **Проверить** (раздел 5): все команды должны пройти.
7. **Обновить документацию:** README, `docs/ADR.md` (ADR-кандидат → ADR с номером), `docs/RELEASE_NEXT.md`, статус задачи в `BACKLOG.md` и в файле задачи.
8. **Коммит и PR.** Сообщения коммитов на английском, в стиле Conventional Commits (`feat:`, `fix:`, `docs:`). Тело PR — по шаблону `.github/pull_request_template.md`. Мёрж — после зелёного CI и ревью.

## 5. Определение готовности (DoD)

Задача готова, когда:

- выполнены все критерии приёмки из файла задачи;
- проходят проверки:
  ```bash
  export PATH=$HOME/go/bin:$PATH
  gofmt -l cmd pkg tests            # пусто
  go vet ./...
  golangci-lint run                 # 0 issues
  go test -race -count=1 ./cmd/... ./pkg/...
  go test -count=1 ./tests/integration/... ./tests/e2e/...
  go build -o /tmp/dhg ./cmd/dhg && DHG_REQUIRE_HELM=1 go test -count=1 ./tests/golden/
  deadcode -test ./...              # нет новых недостижимых функций
  ```
- покрытие нового кода — не ниже порога `codecov/patch` (≈ 86 %; считается по пакетам, без `-coverpkg`, поэтому golden-тесты в него не входят: нужны unit-тесты);
- новое поведение, которое меняет сгенерированный chart, покрыто golden-тестом (`tests/golden/`) с настоящим Helm;
- документация обновлена (шаг 7 раздела 4).
