# Следующий релиз (v1.x)

Ревизия корректности: каждый сгенерированный chart проверяется настоящим Helm, рендер воспроизводит входные манифесты, недостижимый код подключён или удалён. Решения — ADR-045 … ADR-057 в [ADR.md](ADR.md).

## Несовместимые изменения

| Было | Стало | Что сделать |
|---|---|---|
| Объекты переименовывались в `<release>-<chart>-<name>`, селекторы и метки pod'ов заменялись метками chart'а | Сохраняются исходные имена, селекторы и метки (ADR-049) | Повторно сгенерировать chart. Существующие объекты кластера Helm может перенять (`helm install --take-ownership`, Helm ≥ 3.17) |
| CRD рендерились в `templates/` | CRD лежат в `crds/` без шаблонизации (ADR-050) | Обновление CRD — отдельным шагом (`kubectl apply -f crds/`), Helm их не обновляет |
| `--kustomize`: `base` ссылался на шаблоны Helm, патч prod-лимитов `cpu: 1`/`512Mi` | `base` — входные манифесты, overlay'и меняют только `replicas` (ADR-055) | Лимиты для prod задавать патчем в своём overlay или values chart'а |
| Опциональные генераторы — отдельные флаги или недостижимы | Реестр `--with <feature>` и `--feature-opt feature.param=value`, список — `dhg features` (ADR-046) | Заменить флаги на `--with` |
| `--cluster-namespace` (не реализован) | Удалён; фильтр по namespace для всех источников — `--namespace` / `--namespaces` | — |
| `--template-style` (ни на что не влиял) | Удалён; переопределение шаблонов — `--template-dir` и `--template-strategy` | — |
| Зависимость Deckhouse-модуля `helm_lib`, `version: "*"` | `deckhouse_lib_helm`, `version: "~1"` | `helm dependency update` |
| Контейнеры и init-контейнеры в values — списки (`containers: [{name: app, ...}]`) | Map по имени плюс порядок: `containers.<имя>`, `containerOrder`, `initContainers.<имя>`, `initContainerOrder` (ADR-069); `--set services.<svc>.deployment.containers.app.image.tag=X` меняет один контейнер | Повторно сгенерировать chart; `--update` переводит списки в values пользователя в map сам. Свои values-файлы со списками переписать. Контейнер, добавленный в values вручную, добавить и в `containerOrder` |
| Завершённый Job из кластера попадал в чарт обычным объектом и запускался при каждой установке | В values Job — `enabled` и `hook.{enabled,events,deletePolicy,weight}`; Job, завершившийся успешно, получает `hook.enabled: true` (`pre-install,pre-upgrade`; `post-install,post-upgrade`, если Job читает Secret, ConfigMap, ServiceAccount или claim из чарта — до установки их ещё нет), остальные, в том числе упавший Job, — `false`: упавший hook прерывал бы установку и каждое обновление; `enabled: false` убирает Job (ADR-070) | Если Job должен идти обычным объектом — `hook.enabled: false`; порядок запуска — `hook.events` |
| В `spec.template.metadata.labels` Deployment, StatefulSet, DaemonSet, Job и CronJob попадали `helm.sh/chart`, `app.kubernetes.io/version` и `app.kubernetes.io/managed-by`: перенос работающего workload'а под Helm и каждый подъём версии chart'а перезапускали pod'ы | Эти три метки только в `metadata.labels` объекта; в pod template — метки входа и стабильные `app.kubernetes.io/name`, `app.kubernetes.io/instance` (ADR-075) | Первое обновление уже установленного релиза со старым chart'ом один раз перезапустит pod'ы (шаблон изменился); дальше подъём версии pod'ы не трогает. Исключение — Job не как hook (`hook.enabled: false`): `spec.template` у Job неизменяем, поэтому первое `helm upgrade` упадёт с `field is immutable` — перед ним удалить Job (`kubectl delete job <имя>`) или перевести его в `hook.enabled: true`. CronJob это не касается (меняется `jobTemplate`). Выборку pod'ов по `helm.sh/chart` или `app.kubernetes.io/version` заменить выборкой по меткам объекта |
| `--with vault-agent` всегда включал инъекцию, `--env-values` про неё не знал | Параметр `vault-agent.enabled` (по умолчанию `true`); если в chart'е есть блок `vaultAgent`, `values-dev.yaml` содержит `vaultAgent.enabled: false`, а `values-staging.yaml` и `values-prod.yaml` — `true` (ADR-077) | Для dev с Vault задать `vaultAgent.enabled: true` в своём overlay'е. Описание — в разделе README «Секреты по окружениям». В `umbrella` overlay'и родителя переключают `<сервис>.vaultAgent.enabled`, явный `--set` — `--set <сервис>.vaultAgent.enabled=false` |
| Пароли и токены в ConfigMap и в `env.value` (источники `file`, `gitops`, `cluster`) попадали в `values.yaml` как есть | По умолчанию `--redact-credentials=true` (ключ `redact-credentials` в `.dhg.yaml`): значение ключа ConfigMap и `env.value` с именем `*_PASSWORD`, `*_SECRET`, `*_TOKEN`, `*_CREDENTIAL(S)`, `PRIVATE_KEY`, `API_KEY`, `ACCESS_KEY` и значение JVM-опции `-D…Password=`/`-D…Secret=`/`-D…Token=` в любом `env.value` заменяются на `<SET-ME>`; `secretName`, `secretKeyRef.name`, `existingSecret`, `valueFrom` и Secret'ы не меняются; одно `Note:` перечисляет заменённое (ADR-086) | Задать значения через `--set` или вынести их в Secret; прежнее поведение — `--redact-credentials=false` |
| Velero Schedule с `labelSelector` | `orLabelSelectors` (ADR-057) | Velero ≥ 1.10 |
| В separate/library/umbrella два сервиса группы с одинаковым путём values перезаписывали друг друга | Сервис с пересекающимися путями хранит values под своим ключом (ADR-056) | Сверить `values.yaml` таких групп |

## Исправленные ошибки, менявшие данные

- `-s cluster`: у объекта, который ставил Helm, метки `helm.sh/chart` и `app.kubernetes.io/managed-by` (а при совпадении `instance` с релизом — ещё `version` и `instance`) попадали во входные метки chart'а, в том числе в pod template, и оставались там устаревшими; экстрактор их убирает и сообщает, сколько объектов и каких релизов это затронуло.
- Метки входа перезаписывались метками chart'а.
- Значения ConfigMap/Secret получали или теряли финальный `\n`; экстрактор резал документ на `---` внутри блочного скаляра.
- Нулевые значения терялись (`replicas: 0` → 1, `backoffLimit: 0`, `enabled: false`, `minReplicaCount: 0`).
- Image digest разбирался как tag.
- 20 процессоров custom resources теряли поля `spec` вне белого списка (ADR-054).
- `User` (Deckhouse) сохранял пароль в `values.yaml`.
- Одинаковые kind/name в разных namespace и Deployment'ы одного сервиса молча перезаписывали друг друга. Детерминированный выбор имени сервис-группы (`chooseGroupName` в `pkg/generator/grouping.go`) и суффикс `-2` при совпадении нормализованных имён разных групп предотвращают случайную перезапись объектов в зависимости от порядка обхода map.
- `--namespace-resources`: ResourceQuota и LimitRange брали ресурсы «первого workload'а», причём читали их не из того места values — на практике всегда получалась заглушка `1`/`1Gi`/`2`/`2Gi` (LimitRange — `100m`/`128Mi`/`500m`/`512Mi`), и pod'ы группы из нескольких workload'ов отклонялись бы admission'ом квоты. Теперь квота — сумма по всем workload'ам группы (Deployment, StatefulSet, DaemonSet, Job, CronJob) эффективных ресурсов pod'а × пиковое число pod'ов. Ресурсы pod'а считаются как в Kubernetes: сумма контейнеров против максимума init-контейнеров (`max(max(init), sum(containers))`), нативные sidecar'ы (`restartPolicy: Always`) добавляются к сумме; незаданный request берётся из limit, затем из LimitRange. Пиковое число pod'ов: replicas или `maxReplicas` HPA той же группы, плюс `maxSurge` RollingUpdate Deployment'а (по умолчанию 25%); Job — `parallelism` (не больше `completions`); DaemonSet считается для одного узла. Сложение — `resource.Quantity` (`500m` + `1` = `1500m`, `512Mi` + `1Gi` = `1536Mi`); расчёт по каждому workload'у записан комментарием в шаблоне. Значения по умолчанию LimitRange — максимум объявленных в группе (не зависит от порядка входа), `default` не ниже `defaultRequest`. Группа без workload'ов по-прежнему получает заглушку, помеченную в шаблоне.
- separate-режим рендерил 0 объектов, umbrella не генерировался, `values.schema.json` был YAML, HPA/PDB/Gateway/HTTPRoute не рендерились.
- separate/library: безымянный по меткам ConfigMap/Secret/ServiceAccount, на который ссылаются Deployment'ы двух групп с метками, затягивал в первую из групп всех участников второй: один и тот же Deployment, Service и объект попадали в два chart'а. Теперь такой объект остаётся в одной группе, участники групп с метками — в своих.
- Init-контейнеры теряли `restartPolicy: Always`: native sidecar (Kubernetes 1.28+) превращался в обычный init-контейнер, и pod не стартовал. Также сохраняются `resizePolicy`, `volumeDevices`, `terminationMessagePath`/`Policy`, `stdin`, `stdinOnce`, `tty`.

## Новое

- `--with istio-ingress` (ADR-061): Istio `Gateway` + `VirtualService` (`networking.istio.io/v1`) из каждого Ingress — хосты, пути (`Exact`/`Prefix` с семантикой Ingress, `ImplementationSpecific` как префикс), backend'ы с разрешением именованных портов по Service, TLS (`credentialName`) и HTTP→HTTPS redirect (`tls.httpsRedirect`). Ingress остаётся, `istioIngress.replaceIngress` его выключает. `--detect-ingress` при обнаружении Istio (теперь и по `spec.ingressClassName`/аннотации `istio`) больше не молчит: печатает `Note:` — Istio обслуживает Ingress сам, но документация Istio не описывает поддержку аннотаций контроллеров вроде ingress-nginx (redirect, rewrite), а TLS-секрет должен лежать в namespace gateway.
- Поддержка Docker credential helpers (`credHelpers`/`credsStore`) при генерации из образа.
- `dhg profile infer` (ADR-083): выводит платформенный профиль (`--synth-profile`) из Deployment'ов работающего стенда или манифестов — префикс имён, init-контейнеры, `envFrom`, тома, метки, пробы, ресурсы, стратегию выката, тип Service и дополнительные порты, поля контейнера и pod'а, общие для доли `--min-share` Deployment'ов. Флаги: `-s cluster|file`, `-f`, `--context`, `--kubeconfig`, `-n`, `-l`, `--min-share` (по умолчанию 0,9), `-o`, `--values-out`. Имя сервиса и префикс становятся шаблонами, адреса окружения — переменными профиля, а их значения со стенда пишутся в `--values-out`. Описание — в [SYNTH_PROFILE.md](SYNTH_PROFILE.md).
- Генерация из исходников с поддержкой профилей Quarkus, Micronaut и параметром `--image-config`.
- Генерация без манифестов (ADR-058 – ADR-060, [SPEC_SYNTHESIS.md](SPEC_SYNTHESIS.md)): `-s image` (конфигурация образа из registry; учётные данные — из docker `config.json`, включая credential helpers `credHelpers`/`credsStore`), `-s compose` (docker-compose), `-s source` (Dockerfile или, с `--image-config`, config образа; Spring Boot, Quarkus, Micronaut; профили фреймворка → `values-profile-<profile>.yaml`). Невыводимое перечисляется в `SYNTHESIS.md`.

- Источники `cluster` (client-cert, token/`tokenFile`, exec-плагины ExecCredential v1/v1beta1 — kubelogin для OIDC/Dex; `--cluster-secrets skip|mask|include`) и `gitops` (`--git-path`); `--selector` для файлов.
- Процессоры и `--with`-возможности сообщают невыводимое через `Note:`.
- `dhg validate` с разбором шаблонов и матрицей версий Kubernetes API, `dhg graph`, `dhg features`.
- Плагины процессоров (`--plugin`), `.dhg.yaml` (`--config`), `--template-dir`.
- Golden-набор `tests/golden`: lint/template, сохранность объектов, ссылки и селекторы, fidelity, `helm unittest`, post-renderer, `kustomize build`, офлайн-валидатор OpenAPI v3 схем CRD (`tests/golden/crd_schemas/`, 76 схем); CI-job с Helm 3.19.
- `global.namePrefix` (ADR-071): префикс имён всех объектов чарта, чтобы поставить несколько релизов в один namespace (`--set global.namePrefix=a-`). Ссылки на объекты чарта (`envFrom`, `volumes`, `serviceAccountName`, backend Ingress, `scaleTargetRef`, `roleRef`/`subjects`, `parentRefs`/`backendRefs` и др.) получают тот же префикс, ссылки на объекты вне чарта остаются как есть. По умолчанию `""`: имена в рендере прежние; в `values.yaml` появляется `global.namePrefix: ""`, в шаблонах — `include "<chart>.objname"`. CRD, APIService, Namespace и Deckhouse `ModuleConfig`/`User`/`Group`/`NodeGroup`/`*InstanceClass` не префиксуются. Selector Service и PDB при непустом префиксе дополняются `app.kubernetes.io/instance: <имя релиза>` (под'ы несут эту метку), чтобы Service одного релиза не выбирал pod'ы другого; `ingressClassName`, `storageClassName` (в том числе в `volumeClaimTemplates`), `clientConfig.service` у `ValidatingWebhookConfiguration`/`MutatingWebhookConfiguration` и аннотация `kubernetes.io/service-account.name` токен-Secret'а получают префикс, когда объект есть в чарте; объекты, которые создают `--with gateway-api` (Gateway, HTTPRoute, ListenerSet, ReferenceGrant) и `--with golden-signals`, тоже префиксуются, а их `parentRefs`/`backendRefs` следуют за ними.
- Library-режим из реестра (ADR-072): `--mode library --library-ref oci://registry.example.com/platform/platform-lib --library-version "^1.2.0"` не копирует библиотеку в сервисные chart'ы, а объявляет её OCI-зависимостью; library chart пишется под именем из ссылки, чтобы его можно было опубликовать. Те же ключи работают из `.dhg.yaml`. Нужны `helm dependency update` и доступ к реестру.
- Общий chart `--shared-chart <имя>` (ADR-074, режимы `separate` и `library`, ключ `shared-chart` в `.dhg.yaml`): ConfigMap, Secret, ServiceAccount, PVC и другие объекты, на которые ссылаются ресурсы (workload'ы, Ingress, RoleBinding и др.) двух и более сервисных групп, и объекты, на которые не ссылается ни один ресурс, пишутся в chart с этим именем рядом с сервисными; объект, на который ссылается одна группа (в том числе Ingress, RoleBinding или Argo Rollout), остаётся в её chart'е. Ссылки сервисных chart'ов на вынесенные объекты литеральны (`global.namePrefix` сервисного chart'а их не меняет), сам shared chart называет объекты как во входе, а непустой `global.namePrefix` у него — ошибка рендера. Сводка `N shared objects moved to chart <имя>` (список — с `-v`); подсказка установки ставит shared chart первым. Для `universal` и `umbrella` флаг — ошибка.
- `--library-ref` для локальной и HTTP-библиотеки (ADR-084): `file://<путь>` (каталог относительно сервисного chart'а или абсолютный; имя и версия берутся из `<путь>/Chart.yaml`, если каталог уже есть, иначе имя — последний элемент пути; `--library-version` необязателен) и `https://`/`http://` репозиторий chart'ов (обязательны новый флаг `--library-name` и `--library-version`). `repository` пишется как задан, библиотека не копируется в сервисные chart'ы; `oci://` без изменений. Ключ `library-name` — в `.dhg.yaml`. Описание — в README, «Library chart из реестра».
- `--shared-keep` и `--shared-exclude` (ADR-085, ключи `.dhg.yaml`): `Kind/name` объектов, которые остаются в chart'е своей группы (при ссылках нескольких групп — в первой в отсортированном порядке) либо никогда не выносятся в shared chart; записи без объекта дают `Note:`. Объекты shared chart'а получают `helm.sh/resource-policy: keep` (в values объекта; существующие аннотации сохраняются), поэтому `helm uninstall` релиза проекта их не удаляет. Правка общей конфигурации — `helm upgrade ... --set configMaps.<имя>.data.<ключ>=<значение>`, см. README, «Общий chart для общих объектов».
- Выкат, останавливающий старый pod до готовности нового (ADR-076): Deployment с `replicas` не больше `maxUnavailable` (число или процент от `replicas`) или со стратегией `Recreate` получает при генерации `Note:` и находку `BP-HA-004` в `dhg analyze`. Стратегия входа не меняется; заметка показывает значения (`services.<svc>.deployment.strategy.rollingUpdate.maxSurge=1`, `maxUnavailable=0`), которые дают выкат с запасным pod'ом. При `RollingUpdate`, где `maxUnavailable` не меньше `replicas`, `helm --wait` не ждёт готовности pod'а; при `Recreate` простой есть, но `--wait` ждёт новые pod'ы.
- NOTES.txt chart'а с workload'ами: `kubectl -n <ns> rollout status deploy/<имя> --timeout=30m` для каждого Deployment и проверка расхождения `helm get manifest <релиз> -n <ns> | kubectl -n <ns> diff -f -` (код 1 — живое состояние отличается от релиза).
- `-s source`, поиск конфигурации Spring Boot (ADR-082): кроме `src/main/resources` читаются каталоги ресурсов из `pom.xml` (`<build><resources>`, `add-resource` build-helper, выход плагина-генератора) и `<модуль>/*/generated-resources` (в том числе `target/generated-resources`); рекурсивно читаются `spring.profiles.include`, `spring.profiles.active` (только профили, которые приложение включает по умолчанию; dev и test сами не включаются) и `spring.config.import` (`optional:`, `classpath:`, `file:`). Плейсхолдеры всей цепочки становятся переменными приложения. Каталог, который создаёт сборка и которого нет в checkout, даёт `Note:` с подсказкой `mvn generate-resources`. Каталоги ресурсов и файлы `spring.config.import` вне каталога модуля не читаются (`Note: … outside the module, not read`). Порядок `.properties` и `.yml` внутри файлов профиля Spring Boot и Micronaut теперь тот же, что у основных файлов (`.properties` перекрывает YAML; раньше перекрывал `.yml`).
- `-s source --known-keys <файл>` и `--known-keys-from-cluster` (ADR-082): имена переменных, которые платформа уже передаёт контейнеру (строки `KEY` или `источник:KEY`; имена ключей ConfigMap'ов из `envFrom` профиля `--synth-profile`, прочитанные из кластера), не выводятся пустыми обязательными переменными; в `SYNTHESIS.md` строка «N variables come from <источник>». Читаются только имена ключей, значения и Secret'ы — никогда. Оба ключа задаются и в `.dhg.yaml` (`known-keys`, `known-keys-from-cluster`).
- `--with vault-agent`: параметр `enabled` и переключатель по окружениям в `--env-values` (ADR-077); пример `.dhg.yaml` и overlay'ев — в README, «Секреты по окружениям».
- Профиль синтеза (`--synth-profile`, ADR-081): ключи `naming` (имена Deployment, контейнера и Service), `selector` (замена селектора в Deployment, шаблоне pod'а и Service, чтобы совпасть с работающим workload'ом), `service.type` и `service.extraPorts` (`nodePort` не задаётся), `strategy` (`RollingUpdate`/`Recreate`, `maxSurge`/`maxUnavailable`). Все ключи необязательны; без них результат прежний. Описание — в [SYNTH_PROFILE.md](SYNTH_PROFILE.md).

## Исправления интеграции профиля синтеза

- `dhg profile infer`: учётные данные в URL (`user:password@host`) удаляются из профиля и `--values-out` (`Note: credentials in URL of …`); IPv4 и URL внутри текста команды становятся переменными; префикс, общий для большинства Deployment'ов, но не для `--min-share`, попадает в `vars.prefix`; порт Service, обслуживаемый портом приложения под другим номером, даёт `Note`.
- `-s source --known-keys-from-cluster`: имя `envFrom` должно быть именем объекта API (DNS-1123); запрос экранирует имя, ответ не `ConfigMap` и редирект не используются.
- `--mode library --library-ref file://<путь>`: путь без `Chart.yaml` должен указывать на `<output>/<имя>`, иначе ошибка (раньше `helm dependency build` не находил библиотеку); подсказка называет фактический каталог библиотеки.
- `--shared-keep` для объекта, на который никто не ссылается: `Note:` вместо молчаливого отдельного chart'а.
- `Note: unresolved placeholder in Kafka property …` выдаётся только для ключей Kafka и в отсортированном порядке (`SYNTHESIS.md` одинаков между запусками).

## Путь модуля

Модуль переименован в `github.com/AlexGromer/deckhouse-helm-generator` — фактический адрес репозитория; `go install github.com/AlexGromer/deckhouse-helm-generator/cmd/dhg@<версия>` работает начиная с этого релиза. Код, импортировавший пакеты по прежнему пути `github.com/deckhouse/deckhouse-helm-generator`, нужно обновить. Тег релиза — `v1.x`: тег `v2.0.0` и выше Go примет, только если путь модуля оканчивается на `/v2`.

## Известные ограничения

- `--shared-chart`: вынесенные объекты называются как во входе; `global.namePrefix` shared chart'а должен оставаться пустым (иначе `helm template`/`install` падает с ошибкой), для нескольких релизов в один namespace ставьте shared chart один раз.
- Объекты рендерятся в namespace релиза (кроме одноимённых объектов из разных namespace).
- `global.namePrefix` (ADR-071) не применяется к ссылкам внутри `imagePullSecrets`, к именам, которые строят Istio VirtualService/Gateway, egress и остальные `--with`-фичи по именам входа (кроме `gateway-api` и `golden-signals`), к `clientConfig.service` вне `ValidatingWebhookConfiguration`/`MutatingWebhookConfiguration` (APIService, конверсия CRD) и к ссылкам в полях, не входящих в список `<chart>.refs`; такие ссылки остаются буквальными. Родитель Gateway API с явным `namespace` (`--feature-opt gateway-api.gateway-namespace`) тоже остаётся буквальным. `matchLabels` самих Deployment/StatefulSet не содержат метку релиза (менять селектор существующего объекта нельзя), поэтому защита от пересечения — в selector Service и PDB. Если pod'ы входа сами задают `app.kubernetes.io/instance`, selector Service и PDB берёт значение входа.
